# SPEC — что в пути свопа Uniswap подписывается, а что просто calldata

**Публичный артефакт.** Вторая половина разбора, начатого в
`SPEC-uniswap-execution-path.md`. Тот документ ответил «своп не подписывается»; этот
отвечает на следующий вопрос — **что тогда подписывается**, и оказывается, что не только
Permit2.

Прочитано 2026-08-15 по исходникам, пины:
`Uniswap/universal-router` @ `fb25ff09c71dcfc13665e6c65788db737f29e0d4`,
`Uniswap/v4-core` @ `46c6834698c48bc4a463a86d8420f4eb1d7f3b75`,
`Uniswap/v4-periphery` @ `07336f2144f522874e2c3c85e04d1d3f8d5fa471`,
`Uniswap/permit2` @ `cc56ad0f3439c502c246fc5cfcc3db92bb8b7219`,
`Uniswap/v3-periphery` @ `0682387198a24c7cd63566a2c58398533860a5d1`.
Все домены сверены с **задеплоенными** контрактами на chain 1 и chain 8453.

⚠️ **Про пин v3-periphery, честно.** Читал я `0682387…` (ветка по умолчанию), а роутер
пинит подмодулем **другую** ревизию — `b325bb0905d922ae61fcc7df85ee802e8df5e96c`. Сверил
обе: `contracts/base/ERC721Permit.sol` различается **только** прагмой (`0.7.6` против
`0.8.15`), базовым классом (`ERC721` против `ERC721Enumerable`) и переносами строк.
Домен, тайпхеш и построение дигеста в обеих ревизиях идентичны, `IERC721Permit.sol`
побайтово одинаков. И это в любом случае не решающий довод: значения, на которых стоит
документ, сняты с **задеплоенного** контракта, а не с ревизии исходника.

## 1. Короткий ответ

Рабочее понимание «подписывается Permit2, а вызов роутера — нет» **верно в главном и
неполно в деталях**, и обе половины важны.

**Верно:** вызов `execute(bytes commands, bytes[] inputs, uint256 deadline)` не подписан
ничем, кроме обычной подписи транзакции. В `Dispatcher.dispatch()` нет ни одного обращения
к `_setSignatureContext`; типизированная подпись маршрута существует только в отдельной
точке входа `executeSigned`, которой **на боевых адресах нет** (см.
`SPEC-uniswap-execution-path.md` §3 и `vectors/anchor_onchain.sh`).

**Неполно:** подпись потребляет не одна команда, а **три**, и есть **четвёртый путь через
вложение**:

| команда | что уезжает на проверку | кто проверяет |
|---|---|---|
| `0x0a PERMIT2_PERMIT` | `PermitSingle` + подпись | Permit2 |
| `0x03 PERMIT2_PERMIT_BATCH` | `PermitBatch` + подпись | Permit2 |
| **`0x11 V3_POSITION_MANAGER_PERMIT`** | **ERC-721 permit + подпись** | **v3 NonfungiblePositionManager** |
| `0x21 EXECUTE_SUB_PLAN` | ничего сам — но исполняет **вложенный** набор команд, в котором может быть любая из трёх выше | — |

Остальные 19 команд подписи не потребляют: свопы v2/v3/v4, переводы через уже выданный
аллованс Permit2, `SWEEP`, `TRANSFER`, `PAY_PORTION`, `WRAP/UNWRAP_WETH`,
`BALANCE_CHECK_ERC20`, `V4_INITIALIZE_POOL`, оба `*_POSITION_MANAGER_CALL`,
`ACROSS_V4_DEPOSIT_V3`.

Две уточняющие детали, обе важны для политики:

- **`SignatureTransfer` из роутера не достижим вовсе.** Ни одной ссылки на
  `permitTransferFrom` / `permitWitnessTransferFrom` в его исходниках на этом пине.
  Через роутер идёт только семья `AllowanceTransfer`. Подписать `SignatureTransfer`
  агента могут попросить — но не по этому пути, и путать их нельзя.
- **`0x11` не требует, чтобы `spender` был роутером.** Гейт смотрит четыре байта
  селектора и больше ничего; `spender` в проверке не участвует. Значит внутри транзакции
  свопа может ехать permit, отдающий вашу позицию **произвольному третьему адресу**.
  Для политики это означает: allow-list для `spender` здесь несущий ровно так же, как
  в Permit2, и «это же просто своп» не аргумент.

## 2. 🔴 Вторая подписная поверхность: permit позиционного NFT

`Dispatcher.sol:309-311`:

```solidity
} else if (command == Commands.V3_POSITION_MANAGER_PERMIT) {
    _checkV3PermitCall(inputs);
    (success, output) = address(V3_POSITION_MANAGER).call(inputs);
```

Гейт — ровно одна проверка селектора (`V3ToV4Migrator.sol:34-45`): первые 4 байта обязаны
равняться `IERC721Permit.permit.selector` = **`0x7ac2ff7b`**
(`permit(address,uint256,uint256,uint8,bytes32,bytes32)`). Остальной calldata роутер
не разбирает и пересылает как есть.

То есть внутри обычной транзакции свопа может ехать **подпись совсем другого семейства**,
которую проверяет совсем другой контракт со своим доменом.

### Три домена, и они все разные

| | Permit2 | v3 NonfungiblePositionManager | v4 PositionManager |
|---|---|---|---|
| поля домена | 3 | **4, есть `version`** | 3 |
| `name` | `Permit2` | `Uniswap V3 Positions NFT-V1` | `Uniswap v4 Positions NFT` |
| `version` | — | `1` | — |
| сепаратор кеширован | да, immutable | **нет, считается на каждый вызов** | да, immutable |
| нонс | послед. `uint48` / битовая карта | послед. `uint96` **на tokenId** | битовая карта **на владельца** |
| подпись | `bytes` (+ERC-1271, +EIP-2098) | `v, r, s` раздельно (+ERC-1271) | `bytes` (+ERC-1271, +EIP-2098) |

### 🔴 И ловушка, которой не бывает хуже: тайпхеш общий, домен разный

v3 и v4 используют **буквально один и тот же** тайпхеш структуры:

```
Permit(address spender,uint256 tokenId,uint256 nonce,uint256 deadline)
keccak256 -> 0x49ecf333e5b8c95c40fdafc95c1ad136e8914a8fb55e9dc8bb01eaa83a2df9ad
```

У v3 он публичный геттер `PERMIT_TYPEHASH()`, у v4 — константа в
`ERC721PermitHash.sol`. Значения совпадают. Из наших векторов, одно и то же сообщение:

```
hashStruct  v3  105be07e2dbf10f195d3385910838748a21e485c5228bdd036e2330e8e806a62
hashStruct  v4  105be07e2dbf10f195d3385910838748a21e485c5228bdd036e2330e8e806a62   ← побайтово одинаково
digest      v3  9db3d15d7da9a47668891f6cc43ce4f7b8478b97cbf02268d736121e401b98a7
digest      v4  751ba8e3ea454de60b5c8c69bf9d2ac0f9bbc7042ba818831ea4b2208ef46dbf   ← разные
```

Проверка «тайпхеш сошёлся» здесь **успокаивает и ничего не доказывает**. Разводит их
только домен, и ошибка не даёт внятной диагностики: восстановленный адрес просто не равен
владельцу.

### `PermitForAll` — безлимитное разрешение позиционного пути

У v4 есть вторая строка типа:

```
PermitForAll(address operator,bool approved,uint256 nonce,uint256 deadline)
```

`approved = true` отдаёт одному адресу распоряжение **всеми** позициями владельца, включая
те, которых ещё нет. Здесь нет ни `tokenId`, ни суммы — то есть, в отличие от Permit2
с его `type(uint160).max`, **потолок поставить некуда**. Единственная граница, доступная
подписанту, — срок.

Зеркальная ошибка, которую надо назвать до того, как в неё наступили: `approved = false` —
это **отзыв**. Политика, режущая `PermitForAll` целиком, запретит владельцу забрать
у оператора выданный доступ. Тот же класс, что `expiration == 0` в Permit2.

## 3. 🔴 Политика обязана рекурсировать

`Dispatcher.sol:336-338`:

```solidity
if (command == Commands.EXECUTE_SUB_PLAN) {
    (bytes calldata _commands, bytes[] calldata _inputs) = inputs.decodeCommandsAndInputs();
    (success, output) = (address(this)).call(abi.encodeCall(Dispatcher.execute, (_commands, _inputs)));
```

Самовызов проходит, потому что лок его пропускает намеренно (`Lock.sol:14-25`):

```solidity
if (msg.sender != address(this)) { ... } else {
    // The contract is allowed to reenter itself, so the lock is not checked
    _;
}
```

А `msgSender()` возвращает `Locker.get()` — **исходного внешнего вызывающего**, не роутер.
Значит вложенные команды исполняются с личностью того же пользователя.

⇒ Политика, которая разбирает верхний уровень `commands` и на этом останавливается,
**слепа**: `EXECUTE_SUB_PLAN` внесёт внутрь всё, что запрещено снаружи. Разбор обязан быть
рекурсивным, с явным потолком глубины, и запрет `0x21` — честный и дешёвый вариант,
пока рекурсивный разбор не написан и не проверен.

## 4. Ещё одна поправка: деньги не всегда идут через Permit2

`Dispatcher.sol:86` — плательщик выбирается **битом в calldata**:

```solidity
address payer = payerIsUser ? msgSender() : address(this);
```

а `Permit2Payments.payOrPermit2Transfer` разводит эти случаи:

```solidity
if (payer == address(this)) pay(token, recipient, amount);   // обычный transfer, Permit2 не при чём
else permit2TransferFrom(token, payer, recipient, amount.toUint160());
```

То есть на связках «свопнули → полученным заплатили дальше» Permit2 в пути нет вообще, и
рассуждение «наш аллованс Permit2 ограничивает всё» на этой ветке не работает.

Плюс уже сказанное в `SPEC-permit2-signature-transfer.md` §3 и подтверждённое здесь
заново: **получателя средств ни одна подпись Permit2 не несёт**. `to` берётся из calldata
команды.

## 5. Где может стоять наша политика

Разделено по тому, что энклав может проверить **над байтами запроса, ничего не зная
о внешнем мире**, и что не может.

**Может — структурно:**

1. Семейство подписи определяется однозначно: домен + тайпхеш. Всё, что не входит в
   утверждённый список, — отказ. Список сегодня: Permit2 (`PermitSingle`, `PermitBatch`,
   `PermitTransferFrom`, `PermitBatchTransferFrom`, оба witness-варианта), v3 NFT `Permit`,
   v4 NFT `Permit` и `PermitForAll`.
2. `spender` / `operator` ∉ allow-list → отказ. Несущая проверка, но **сверять надо
   разное в разных семьях**:
   - `AllowanceTransfer` (`PermitSingle`/`PermitBatch`) и оба NFT-permit'а: `spender` —
     поле подписываемой структуры, сверяем его;
   - `SignatureTransfer`, включая witness-варианты: поля `spender` в структуре **нет**,
     Permit2 хеширует туда `msg.sender`. Сверять надо адрес, который будет вызывать
     Permit2, и он обязан прийти в запросе явно, без значения по умолчанию;
   - `SignatureTransferDetails.to` — **отдельный случай, и проверить его нельзя**:
     получатель в подпись не входит вовсе, это calldata предъявителя.
3. `token` ∉ allow-list, сумма выше потолка (в сырых единицах) → отказ.
4. `amount == type(uint160).max` в AllowanceTransfer → отказ, независимо от потолка.
5. `PermitForAll(approved = true)` → отказ вне узкого списка; `approved = false`
   пропускать всегда (это отзыв).
6. Сроки (`expiration`, `sigDeadline`, `deadline`) выше абсолютного потолка → отказ.
   Абсолютный потолок часов не требует.
7. Для транзакции роутера, если её вообще подписывать: `to` = проверенный адрес роутера
   этой сети, `chainId` ожидаемый, байт команды ∈ узкий список, **разбор рекурсивный**
   (§3), все `Currency` и `hooks` каждого `PoolKey` ∈ allow-list, итоговый получатель
   после разбора всей последовательности — владелец. Поле защиты от проскальзывания
   **зависит от команды**: у exact-in это `amountOutMinimum`, у exact-out —
   `amountInMaximum`. Проверять только первое — значит оставить exact-out без защиты
   и не заметить этого.
8. Ненулевые биты выше 159-го в адресном слове → отказ.

**Не может, и это границы, а не недоработки:**

- **Нонс v3.** Он не параметр `permit()`: контракт делает
  `_positions[tokenId].nonce++` и подставляет прочитанное значение в хеш. Подписант
  обязан узнать его из состояния цепочки, а энклав состояния не видит. Ошибка безобидна
  (подпись не примут), но «мы проверяем нонс» говорить нельзя.
- **Владельца позиции.** В структуре его нет ни в v3, ни в v4: контракт читает
  `ownerOf(tokenId)` / `_ownerOf[tokenId]` в момент исполнения и сверяет с восстановленным
  адресом. То есть подпись привязывается к владельцу **поздно**. Энклав не знает, чей
  сейчас `tokenId`, и не может проверить, что подписывает разрешение на **свою** позицию.
- **Что представляет собой `tokenId`.** Какая пара, какой диапазон, сколько там
  ликвидности — всё это состояние цепочки.
- **Добросовестность spender'а, хука и токена.**
- **Содержимое `hookData`.** Произвольные байты, уезжающие в произвольный контракт хука.

## 6. Мелочи, которые всё-таки стоит знать

- **v3 требует `spender != ownerOf(tokenId)`** и ревертит иначе. Политика, подставляющая
  владельца в `spender` «по умолчанию», сломает каждый запрос.
- **Домен v3 не кеширован** — считается на каждый вызов из живого `chainid()`. У Permit2
  и v4 он immutable и пересчитывается только при смене `chainid`. На форке эти три
  контракта поведут себя по-разному.
- **Малleability.** Ни v3 (`ecrecover` на сырых `v,r,s`), ни `SignatureVerification`
  Permit2/v4 не требуют канонической low-s формы. Повторного использования это не
  открывает — нонс сжигается, — но подпись **не является уникальным идентификатором**
  разрешения. Наш подписант отдаёт low-s и без этого требования.
- **`V4_POSITION_MANAGER_CALL` фильтрует не то, что обещает.** Комментарий в коде говорит
  «we only allow Actions.MINT», а `_checkV4PositionManagerCall` — это **deny-list из
  четырёх** действий (`INCREASE_LIQUIDITY`, `INCREASE_LIQUIDITY_FROM_DELTAS`,
  `DECREASE_LIQUIDITY`, `BURN_POSITION`). Из 28 действий `Actions.sol` проходят 24 —
  включая `MINT_POSITION_FROM_DELTAS`, который в том же `Actions.sol` помечен
  `DEPRECATED: Vulnerable to sandwich attacks - do not use`. Подписи это не касается,
  но читать комментарий вместо кода здесь дорого.

## 7. Чего мы не гарантируем — здесь то же, что и раньше

Полностью — `SPEC-enclave-guarantee-boundary.md`. Ничего из разобранного выше границу не
двигает: цену исполнения, защиту от MEV и величину проскальзывания энклав не обещает.
Разбор добавил к списку недоступного ровно три пункта, все — состояние цепочки: нонс v3,
владелец позиции и содержимое `tokenId`.

## 8. Как проверить это самому

```bash
python3 verify_nft_ours.py     # путь A: наш кодировщик, только stdlib
node   verify_nft_sdk.mjs      # путь B: viem
python3 falsify_nft.py         # восемь мутаций, каждая обязана покраснеть
./anchor_onchain.sh            # якоря у задеплоенных контрактов (нужна сеть)
node   onchain_fieldorder.mjs  # порядок полей судит сам Permit2 (нужна сеть, §8a)
```

Семь векторов, обе семьи, обе сети. **Каждый вектор несёт доменный сепаратор, снятый
с задеплоенного контракта**, и путь A сверяется с ним — то есть чтение исходника про
«есть ли поле `version`» проверяется цепочкой, а не нашим мнением.

**Честно о независимости путей.** Для Permit2 второй путь берёт типы из
`@uniswap/permit2-sdk`, то есть ловит неверное чтение исходника. Здесь опубликованного
SDK нет, viem получает типы от нас и проверяет **кодировщик, а не чтение**. Чтение
проверено иначе: домен — якорем у цепочки, тайпхеш v3 — публичным геттером
`PERMIT_TYPEHASH()`.

## 8a. 🔴 Порядок полей: пробел закрыт, судья — сам контракт

В первой редакции здесь стояло: «остаётся непроверенным сторонним источником порядок полей
внутри структуры — оба пути берут его из одного чтения». Это была настоящая дыра, и вот
почему она опаснее, чем звучит: тайпхеш её не ловит. Тайпхеш — это хеш **строки типа**,
а строка правильная; неправильна была бы наша **конкатенация**. Оба офлайн-пути сошлись бы
на одном и том же неверном дигесте, и весь набор векторов промолчал бы.

Это не гипотеза. 2026-08-15 живой ордер на Hyperliquid был отвергнут ровно по этой причине:
порядок полей внутри подписываемого действия отличался от канонического (`s` перед `r`),
площадка пересобрала полезную нагрузку по-своему, дигест уехал, восстановился чужой адрес.
Валидная подпись, не те байты, никакой внятной диагностики.

Закрыто так: **дигест считает наш код, а судит его задеплоенный контракт**
(`vectors/onchain_fieldorder.mjs`, `eth_call`, ничего не отправляется).

- **Положительная проверка.** Permit2 принял подпись над дигестом, посчитанным путём A.
  Контракт восстанавливает подписанта из **своего** дигеста и сверяет с владельцем; если бы
  наша конкатенация отличалась, он бы восстановил чужой адрес. Принял — значит побайтово
  собрал то же, что и мы.
- **Отрицательная проверка.** Переставляем `expiration` и `nonce` — **оба `uint48`**, так что
  строка типа, тайпхеш и все ширины остаются верными, меняется только порядок. Контракт
  отвечает `InvalidSigner` (`0x815e1d64`). Значит проверка умеет краснеть, и положительная
  что-то значит.

Тот же класс добавлен и в офлайн-фальсификации: `expiration`/`nonce` в Permit2 и
`tokenId`/`nonce` в NFT-permit (там **три из четырёх полей — `uint256`**, перестановка
невидима вообще ни для какой типовой проверки).

**Что осталось непроверенным контрактом:** порядок полей в NFT-permit'ах. У Permit2 проверка
возможна, потому что `permit()` принимает любого `owner`; у позиционных NFT контракт читает
`ownerOf(tokenId)`, и для положительной проверки нужна реальная позиция, принадлежащая
нашему пробному ключу. Офлайн-мутация есть, контрактного подтверждения нет — так и записано.

## 8b. 🔴 Побочная находка: EIP-7702 отключает проверку подписи

Первый прогон проверки выше упал, и причина оказалась содержательной. Я взял общеизвестный
тестовый адрес anvil, а у него **на mainnet стоит делегация EIP-7702** — его код
`0xef0100…`. Значит `claimedSigner.code.length != 0`, и `SignatureVerification.verify`
уходит в ветку **ERC-1271**: вызывает `isValidSignature` у делегата вместо `ecrecover`.

Следствие общее, не про тестовый ключ: **если у владельца стоит 7702-делегация, наша
подпись не проверяется вовсе** — судьбу решает контракт делегата. Для подписанта это вход,
которого он не видит и не контролирует: код по адресу владельца — состояние цепочки.
В `onchain_fieldorder.mjs` стоит явный гейт на этот случай, чтобы проверка не отчитывалась
зелёным, измеряя не то.

## 9. Границы того, что доказано этим документом

Доказано: перечисление 23 команд и их классификация по потреблению подписи; три домена
и совпадение тайпхешей v3/v4; воспроизводимость всех дигестов двумя путями; совпадение
четырёх доменных сепараторов с задеплоенными контрактами; рекурсивность
`EXECUTE_SUB_PLAN` и пропуск лока при самовызове.

**Не доказано:** что перечисление команд полно относительно будущих версий роутера
(проверено на пине); что энклав это подписывает — интеграции нет; поведение хуков
в реальных пулах — мы читали интерфейс, а не задеплоенные хуки.
